## How we work (keep doing this)
- **Plan first, then one step at a time.** For each step:
  1. Implement it.
  2. Compile-check it.
  3. The user runs the EditMode tests and play-tests in the Editor.
  4. **One commit per step on `main`** (`feature - …` / `Balance - …` / `fix - …` / `UI - …`, with a body).
- **The Unity Editor stays open,** so batchmode can't run. Compile-check with `dotnet build` on scratch copies of the generated csproj files (see the memory "compile-check-without-unity"). The script must also drop `<Compile>` entries for deleted files.
- **Assets:**
  - Claude creates assets of new SO types directly (YAML + `.meta`, script GUIDs from the `.cs.meta`).
  - **Effect items only go through the SQLite DB** (`Database/effects.db`). Claude may write rows with a Python `sqlite3` script after backing the DB up; each DB write needs the user's approval. The user then runs Tools → Effects → Generate ScriptableObjects. Never hand-make Effect `.asset` files.
  - Bigger UI prefabs are generated by an editor builder script (see `SkillTreePanelBuilder`) rather than hand-written YAML.
- **Tests** live in `Assets/Scripts/Tests/Editor/`: pure tests for the math, guard tests over the real assets. A guard test may skip (`Assert.Ignore`) only until its content exists, then it must fail instead.
- **Tunables never get hardcoded.** They go in a settings SO or an Inspector field.
